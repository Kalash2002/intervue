# Grader notes: Multiply Strings

Same sizes and rules as the classic version (1 to 200 digits each, digits only, no leading zero except `"0"`). The statement forbids converting either operand to `int`, `long`, `BigInteger` or `BigDecimal`. The tests cannot enforce that: a scratch variant that multiplies with `BigInteger` passes every test, which is acceptable; the walkthrough says why an interview rules it out, and a reviewer reading the code sees it. Converting to a `long` fails, since the operands go far past 19 digits. The tests compare strings in quotes, so `""` and `"0"` read differently in a failure message, and long numbers are shown by length and first digits. The result is a single number, so there is only one correct output.

Expected values are hand-checked strings for the fixed cases and `BigInteger` products, computed in the test, for the seeded long and random pairs.

Tests cover: the sample (`"4096" x "735"`, every position of the product used; `"99999" x "9999"`, carries throughout; `"0" x "58173"`); a zero operand, on either side and with a 200-digit number; products one digit shorter than the two operands together, where no leading zero may be left (`"15" x "6" = "90"`, `"101" x "11"`, `"5" x "1"`, `"1" x "1"`, and `"8" x "9"` beside them, which uses both digits), and products with zeros inside or at the end that must stay (`"25" x "4" = "100"`, `"125" x "8"`, `"250" x "40" = "10000"`, `"138" x "29" = "4002"`); carries through long numbers (200 nines times 9, 200 fives times 4, 40 nines times 99, 120 fours times 25, and 10^199 times 10); a 200-digit number times `"1"`, and products with powers of ten; both operands long (200 nines squared, 10^199 squared, `"0"` times 200 nines, `"1"` times a 199-digit number, and a seeded pair of 200-digit numbers in both orders); and 300 seeded random pairs of 1 to 200 digits, with about one operand in 25 equal to `"0"`.

The traps the walkthrough and hints name, each run as a scratch variant: going through a `long` fails 5 of 7; reading the whole position array, leading zero included, fails all 7; dropping every zero digit instead of only the leading ones fails 6; and returning the empty string for a zero product fails 4. One more was run: the Better's rows built without their last carry fail 5. Adding all the digit products into their positions first and carrying once at the end, from the right, is correct and passes.

Timing: `bothOperandsLong` has a limit of 500 ms and `randomPairs` one of 1,000 ms (3x is 1,500 and 3,000 ms). The reference took 12 to 16 ms on the first and 72 to 109 ms on the second over six cold runs, much of the second spent in the test's own `BigInteger` products; the limit on `randomPairs` is 1,000 ms so that the best run stays under an eighth of it. The naive solution is the walkthrough's Brute force, adding `num1` to a total `num2` times, which needs up to 10^200 additions: with the limit raised 10 times it does not finish either test in 5,000 and 10,000 ms. Counting up to the smaller operand instead, the mirrored brute force, does not finish them either. The walkthrough's Better, one row per digit, is O(n · (m + n)) and passes (122 ms on `randomPairs`).
