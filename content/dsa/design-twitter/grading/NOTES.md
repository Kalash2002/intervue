# Grader notes: Design Twitter

Tests drive a `Twitter` object through sequences of calls and compare each feed with the expected list, order included. They cover: the sample (following shows older posts, unfollowing hides them), newest first across several authors with an unfollowed author's post in between and ids that do not follow time (Example 2), following yourself (`follow(3, 3)` must not list post 900 twice; a version that adds the user to its own follow list does) and unfollowing yourself (your posts must stay; a version that keeps the user in its own follow set and removes it here returns an empty feed), an empty feed, the cap of ten, unfollowing someone not followed and following twice, follow going one way, ids at the limits (user 0, user 10,000, post 0, post 10^9), eleven visible posts interleaved with an unfollowed author's four, two objects that must not share state, and a large test.

The large test has 200 readers (users 1000..1199), each following 20 of the authors 0..499. Each author posts once per round for 20 rounds, in order of user id; then users 500..999, whom no reader follows, make 100,000 newer posts. The test then requests 70,000 feeds, 350 per reader. A reader's newest ten are the last-round posts of its ten highest-numbered authors, in descending order of author, and the test builds that list itself. In all it makes 184,000 calls, within the limit of 200,000.

The naive solution keeps one global list of posts and walks it from the newest end for every feed, so each feed skips the 100,000 posts by strangers: 7 * 10^9 steps, which exceeds the limit and 3x the limit. The reference keeps each author's posts in their own list and merges the visible lists with a heap. The walkthrough's Better (collect the last ten posts of each visible author and sort) is about four times slower than the reference here and passes.
