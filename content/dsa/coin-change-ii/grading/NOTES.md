# Grader notes: Coin Change II

The rules are the classic ones: up to 300 different values from 1 to 5,000, amounts up to 5,000, and the answer is less than `2^31`. The statement says outright that only the count for `amount` is guaranteed to fit, and that counts for smaller totals can pass even the `long` range. Java's `int` addition wraps modulo 2^32, so every table entry is right modulo 2^32 and the answer, below 2^31, comes out exact; a `long` table cast back to `int` passes too. Only one answer is possible, so no tie rule is needed.

Tests cover: the sample (`[3,5,8]` for 16 gives 3, `[4,9,7]` for 18 gives 2, an amount of 0 gives 1); order not mattering (`[2,5]` and `[5,2]` for 12 give 2, where counting orders gives 4); a value used many times (`[9,4]` for 36 gives 2, nine 4s or four 9s); no handful (`[6,4,10]` for 15, all even, gives 0); values larger than the amount (`[7,20,2]` for 11 gives 1, `[30,4999,5000]` for 60 gives 1, `[4999,5000]` for 0 gives 1); 300 seeded random tills of 2 to 4 values from 1 to 12 and amounts up to 30, checked against a search in the test over every number of coins of each value; 300 values, 2001 to 2300, for 4,500, which gives 51 (no single value is 4,500, three coins are more than 4,500, and the pairs run from 2200 + 2300 to 2250 + 2250); and three large amounts. The even values 40, 38, ..., 2 for 4,999 give 0, while the count for 4,998 is a 30-digit number. `[1,3,4,7]` and `[7,4,3,1]` for 5,000 give 249,133,433: for each number of 7s and of 4s, the number of 3s can be anything from 0 to what is left divided by 3, and the 1s make up the rest; that sum, computed separately, agrees with the table.

Traps, each checked with a scratch solution: totals on the outer loop (counting orders) fails the sample, the order test, the large-values test, the random test, the 300 values (101) and both large amounts; totals run downwards (each value once) fails eight tests, the 300 values among them (50: 2250 + 2250 needs one value twice); a memo keyed by the amount left alone counts orders and fails the same as the swapped loops; `Math.addExact` throws on the even values.

The three large tests have a limit of 200 ms each (3x is 600 ms). The reference, one array with the values outside, finishes each in about a millisecond. The naive solution is the walkthrough's brute force, which decides the values in order one coin at a time; it is still running after 4 s on all three, past the limit and 3x. Its recursion is at most 5,004 deep on these tests (the reversed order reaches that depth at once), which fits in the default stack, so it times out rather than overflowing it. The walkthrough's Better, the memoised recursion, is O(k × amount) like the reference and passes; at the largest depth the constraints allow, 300 values with a 1 last and an amount of 5,000, its recursion is 5,300 deep, and a scratch run of that depth on the test thread fits, also with the JIT off.
