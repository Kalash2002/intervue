# Grader notes: Non-overlapping Intervals

Deviation from the classic version: minutes run from 0 to 10^9 (the classic uses -5 * 10^4 to 5 * 10^4); the size, up to 100,000 requests, and the touching rule are the classic ones. Requests are half-open, so two that only touch, one ending at the minute the other starts, can both stay; the statement says so, and the tests check that boundary (comparing with `>` instead of `>=` fails the sample, the touching test, the test of one long request over two touching ones, the random test and the second timed test). The answer is a count, so there is only one correct output.

Tests cover: the sample (Example 1 defeats keeping the request that starts first, Example 2 defeats cancelling the longest and keeping the shortest, Example 3 is two identical requests); touching requests, in order and out of order; keeping the first to start (`[[2,14],[3,6],[7,10],[11,13]]` and `[[10,40],[12,14],[15,18],[20,21]]`, 1 each, where it gives 3); cancelling the longest (`[[100,200],[190,205],[203,210],[208,300]]`, 2, where cancelling the longest first, or dropping the longer of each overlapping pair in order of start, gives 3); keeping the shortest (`[[0,5],[4,7],[6,11]]`, 1, where it gives 2); one request, including one over the whole range; five identical requests (4); one long request over two that touch (`[[30,60],[30,45],[45,60]]`, 1); three requests with the same end (2); 300 seeded random lists of 1 to 10 requests, checked in the test against every set of requests; and two timed lists of 100,000 requests. The three wrong rules are the ones the statement, the walkthrough and the Level 1 hint name; each was run as a scratch variant and fails the tests listed.

The first timed list is `[i, i + 50,000)` for every i below 100,000, listed from the last to the first: only two requests fit, so 99,998 are cancelled, and every request overlaps half of the others. The second is `[i / 2, i + 1)`, the odd ones listed first and then the even ones: 16 requests fit, so 99,984 are cancelled, and each request's latest compatible predecessor sits about half way down the list before it. The lists are not shuffled so that the reference's sort stays cheap (a shuffled sort of 100,000 rows costs 70 to 120 ms on a cold JVM); every slower approach sorts first, so the order cannot help them.

Both timed tests have a limit of 400 ms (3x is 1,200 ms). The reference, keep the request that ends first, took 14 to 19 ms on the first and 12 to 15 ms on the second over six cold runs. The naive solution is the walkthrough's Better, the longest chain ending at each request, which compares every pair; it does not finish either list in 8 s. The naive is the Better rather than the Brute force because the brute force recursion, one call per request, ends with a `StackOverflowError` on both timed lists, which verify reads as a failure rather than a timeout; it still fails both timed tests. Two quicker forms of the table, which sort by end and look for the latest compatible request by scanning down from the request before, or up from the first, take over 4 s on both lists and 1.8 to 3.4 s respectively. Sorting by start and cancelling the later-ending of each overlapping pair, and the table with a binary search, are O(n log n) and pass.
