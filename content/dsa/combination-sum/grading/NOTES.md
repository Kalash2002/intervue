# Grader notes: Combination Sum

Results are compared after sorting each combination and then the list, because any order is allowed; a combination listed twice stays in the compared list twice, so repeats fail. Tests cover: the sample, values used different numbers of times, every candidate larger than the target (empty answer), one value used three times (a version that moves past a value after using it once fails), a target that is itself a candidate, two values whose orderings give many sequences but only two combinations (a version that builds ordered sequences without removing repeats lists the same combination several times and fails), candidates given largest-first (a version that stops its loop at the first value that is too big without sorting first returns nothing for `[9, 2]` with target 4 and for `[13, 4, 11]` with target 12), and the limits (a value equal to 40, twenty 2s, a target of 1).

The large test uses the 30 candidates 2 to 31 in a seeded shuffled order with target 40, which has 6,131 combinations. The test counts them itself with the standard coin-counting table, checks that every returned combination uses only candidates, adds up to 40 and appears once, and then that the count matches, so a missing combination fails.

The naive solution tries every value at every step, so it builds each combination once per ordering of its values, then sorts each one and removes repeats with a set. On the large test that is tens of millions of sequences; it did not finish in 20 s in a scratch run, against a 1,000 ms limit (3x is 3,000 ms). The reference sorts and only lets a combination continue with the current value or a later one; it took about 3 ms on the large input in the same scratch run.
