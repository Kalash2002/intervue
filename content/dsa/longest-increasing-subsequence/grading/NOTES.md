# Grader notes: Longest Increasing Subsequence

The array may hold up to 200,000 values from -10^9 to 10^9 (the classic version allows 2,500 values from -10^4 to 10^4). At that size the O(n²) table, the walkthrough's Better approach, is graded as too slow: the statement's sizes, the timed tests and the walkthrough all say so, and the O(n log n) smallest-end list is what passes.

Tests cover: the sample; equal values that must not extend a pick (`[2,2,4,4,8,8]` gives 3, `[-1,-1,-1,0]` 2, `[3,3]` 1; searching for the first end greater than the value, which allows equal values, gives 6, 4 and 2, and fails Example 2 with 5); picks that skip positions (`[3,1,4,2,5]` gives 3 and `[10,1,11,2,12,3,13]` gives 4; the longest rising run of neighbours gives 2); taking the next larger value at once (`[2,9,3,4,5]` gives 4, which greedy from every start gets as 3; `[9,1,2,3,10]` gives 4, where starting at the first value gives 2; `[5,6,7,1,2]` gives 3, where starting at the smallest gives 2); a single value; values at the limits (`[1000000000,-1000000000,0,999999999]` gives 3); 300 seeded random arrays of 1 to 12 values from 0 to 7, checked against a search in the test over every set of positions; and four arrays of 200,000 values: 400 falling blocks of 500, each block above the one before (400, one value per block); a rise in equal pairs from -10^9 (100,000, one of each pair; the non-strict search gives 200,000); the evens 0 to 199,998 rising, then the odds 199,999 down to 1 (100,001: all the evens, then 199,999, since the odds fall); and the same evens, then 100,000 ones (100,000: a 1 can only follow the 0 and the ones are equal, so the evens alone are longest; the non-strict search gives 100,001).

The four large tests have a limit of 300 ms each (3x is 900 ms). The reference finishes each in about 5 to 15 ms. The naive solution is the walkthrough's Better approach, the O(n²) table, because that is the slower approach the constraints are set to rule out; it takes about 27 s per large test, far past the limit and 3x. The walkthrough's Brute force, every rising pick from every start, is exponential: it times out on the falling blocks and overflows the stack on the three long rises, so it fails all four. Walking the list of ends one by one instead of the binary search is O(n × answer). From the front it takes about 2.3 s or more on the rise in pairs and 1.7 s or more on each of the two tests that start with the evens, whose rise alone costs it about 5 × 10^9 steps. From the back it is quick on a plain rise; on the evens-then-odds test the k-th odd lands k places from the end, so the odds land at every depth and the scan walks about half the list on average (1.2 to 10 s, depending on the JIT); on the evens-then-ones test every 1 lands at position 1, so the scan walks the whole list of 100,000 each time, about 10^10 steps, 3 to 16 s here. `Arrays.binarySearch` on the list, which is strictly increasing, passes.
